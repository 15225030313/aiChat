## 第一部分：RAG 到底是什么（先建立直觉）

### 1.1 一个类比：开卷考试

大模型很聪明，但它**没读过你公司的文档**。直接问它「我们公司的报销流程是什么」，它要么瞎编（幻觉），要么说不知道。

RAG（Retrieval-Augmented Generation，检索增强生成）就是**让模型开卷考试**：

```
闭卷考试：直接问模型 → 模型凭"记忆"（训练数据）回答 → 会编造
开卷考试：先从资料里翻到相关那几页 → 把那几页和问题一起给模型 → 照着资料回答
         ↑这一步就是"检索(R)"          ↑这一步就是"生成(G)"
```

### 1.2 但"翻书"有个大问题：书太厚，怎么翻得快？

人翻书靠目录和直觉，计算机靠什么？靠**向量化**：

- 把每段资料变成一串数字（向量），语义相近的段落，数字串也相近
- 把你的问题也变成数字串，然后找"数字串最接近"的几段——这就是语义检索

所以完整流程是：

```
提前准备（只做一次）：文档 → 切成小段 → 每段变向量 → 存进向量库
用户提问（每次）：    问题 →变向量→ 找最像的几段 → 塞进Prompt → 模型回答
```

**记住这两条链路，阶段二所有工作就是把它们用代码实现出来。**

### 1.3 名词小词典（遇到不懂回这里查）

| 名词 | 大白话解释 |
|------|-----------|
| Chunk（分片） | 把长文档切成的小段，一段 300-500 字，检索的基本单位 |
| Overlap（重叠） | 相邻两片之间重复的部分，防止知识恰好在切分处被切断 |
| Embedding（向量化） | 把一段文字变成一串数字（如 1024 个小数），代表它的"语义" |
| 向量 / 维度 | 上面那串数字就是向量；有多少个数就是多少维（bge-m3 是 1024 维） |
| 余弦相似度 | 衡量两个向量"方向"像不像的分数，越接近 1 越相似 |
| 向量库 | 专门存向量和做相似度搜索的数据库，本项目用 Chroma（单机、零配置） |
| 召回（Recall） | 从库里粗略找出 TopN 个可能相关的片段（快，但不一定准） |
| Rerank（重排） | 对召回的 TopN 精细打分排序，取出真正相关的 Top5（慢一点，但准） |
| Prompt 注入 | 把检索到的片段写进提示词里给模型看 |
| 幻觉 | 模型一本正经地编造事实 |
| 溯源 | 回答里标注"这个结论来自资料第几段"，可点开看原文 |

1. 为什么问题和文档要用**同一个** Embedding 模型？（不同模型的"数字语言"不通用，算出的相似度无意义）
2. Chroma 的 query 返回的 distance 越小代表什么？（越相似）

## 第四部分：常见坑（提前知道，少熬三个夜）

1. **Embedding 模型不一致**：入库用 A 模型、查询用 B 模型 → 相似度全错且不报错。规定：`embed.py` 是唯一入口。
2. **中文分片乱码**：TXT 没探测编码，GBK 文件按 UTF-8 读全是乱码 → 用 `chardet`。
3. **Chroma 忘了持久化**：用内存模式（`EphemeralClient`）重启全丢 → 用 `PersistentClient(path=...)`。
4. **召回片段太多撑爆上下文**：Top5 × 500 字 ≈ 2500 字，安全；别贪心召回 Top50。
5. **API 批量限制**：Embedding 一次最多 N 条文本，超限报错 → embed.py 里做分批。
6. **评估集太随手**：测试问题必须是"库里真有答案"的，否则命中率无意义。

## 第五部分：面试怎么讲（背下这几问）

| 面试官问 | 你答（30秒版） |
|---------|---------------|
| 什么是 RAG，为什么需要？ | 模型没见过私有数据，直接问会幻觉；RAG 先检索相关片段注入 Prompt 让模型开卷回答，成本低、可溯源、知识可随时更新 |
| 分片为什么要重叠？ | 防止关键信息恰好在切分边界被切断，overlap 保证至少一个片段语义完整 |
| 召回后为什么要 Rerank？ | 向量检索是粗排快但排序不准；Rerank 用交叉编码器逐对精算，Top20→Top5，是效果与成本的平衡 |
| 怎么缓解幻觉？ | Prompt 强约束"只根据资料回答"+ 没有就明说 + 溯源标注 + 检索不到时不调用模型 |
| 怎么评估检索效果？ | 建 20 条标注测试集，测 TopN 命中率；对比加/不加 Rerank 的提升（报真实数字） |
