## 一、全景：两条链路

```
【链路一：知识库创建】（上传时一次完成，用户无感知）
上传 PDF ──→ 解析提取文本 ──→ 清洗 ──→ 滑动窗口分片 ──→ SQLite 存原文分片
                (parse.py)                    (chunk_text)      (kb_store.py)
                                                          │
                                    硅基流动 bge-m3 向量化 ←┘ (embedding.py)
                                                          │
                                    存入 Chroma 向量库 ──→ 标记 vectorized=1
                                    (vector_store.py)      (kb_store.py)

【链路二：知识库应用】（每次带库提问时实时发生）
用户问题 ──→ 问题向量化(同一个模型!) ──→ Chroma 语义检索 Top5
                                              │
        召回片段拼进 system prompt ←───────────┘
                │
        DeepSeek 流式生成（带 [1][2] 引用编号）
                │
        SSE 流推回前端：先发 sources 引用元数据，再逐字发正文
```

核心思想一句话：**创建时把知识切块存成向量；应用时把问题也变成向量，找「意思最相近」的几段原文，塞给大模型开卷作答。**

## 二、知识库创建（上传链路）

### 2.1 API 入口 — `backend/main.py` 的 `kb_upload`

```python
@app.post("/api/kb/upload")
async def kb_upload(file: UploadFile = File(...)):
    # 1. 格式白名单校验（.pdf）+ 大小校验（≤10MB）
    # 2. save_upload_file()：原始文件留档到 uploads/
    # 3. parse_file_path_safe()：落临时文件 → 解析出纯文本
    # 4. chunk_text(text)：切成 500 字/片的分片
    # 5. add_document(...)：文档元数据 + 分片写入 SQLite
    # 6. vector_store.vectorize_document(doc_id)：向量化入 Chroma
```

**设计要点**：第 6 步向量化用 try/except 包住——向量化失败**不阻塞上传**，文档标记保持「待处理」，管理页有「向量化」按钮可手动重试（`POST /api/kb/vectorize/{doc_id}`）。这就是你今早上传 knowledge1/knowledge2 时，列表直接显示「已入库」的原因。

### 2.2 解析与分片 — `backend/rag/parse.py`

**文本提取**（pymupdf 逐页）：

```python
def extract_pdf_text(file_path):
    with pymupdf.open(file_path) as doc:
        for page in doc:
            parts.append(page.get_text("text"))  # 每页取纯文本
```

**清洗**（`clean_text`）：统一换行符 → 去行尾空格 → 连续空行压成一个。

**分片**（`chunk_text`，RAG 效果的第一决定因素）：

```python
CHUNK_SIZE = 500    # 每片目标长度（字符）
CHUNK_OVERLAP = 100 # 相邻片重叠长度
step = chunk_size - overlap   # 每片实际向前推进 400 字
```

滑动窗口：片1=[0,500)，片2=[400,900)，片3=[800,1300)……

> **面试考点（必问）**：为什么要有 overlap？
> 一句关键知识恰好被切断在两片边界时，重叠区保证至少一片包含完整上下文；否则检索召回的可能是半句话，回答质量直接崩。
> 另一个常见追问：为什么 500 不是 1000？——片太短上下文不足，太长则单向量表达不了多重语义（且塞进 prompt 更贵），500+100 是中文场景的常用起点，**参数可调可实验**才是关键态度。

### 2.3 元数据存储 — `backend/rag/kb_store.py`（SQLite）

两张表：

```sql
documents (id, filename, size_bytes, chunk_count, vectorized, created_at)
chunks    (id, doc_id, chunk_index, text)
```

- `chunks` 表保存**原文分片**，是向量化的数据源，也是将来 ReRank/评估的底账；
- `vectorized` 列是 SQLite 与 Chroma 的**同步标记**：0=待处理，1=已入库；
- 删除文档时 `main.py` 会**同时**调 `delete_document()`（SQLite）和 `vector_store.delete_doc()`（Chroma），两边永远保持一致。

> **面试考点**：为什么向量库里还要留一份 SQLite？
> Chroma 只擅长「向量+元数据」的检索，管理页列表、原文溯源、统计这些关系型查询用 SQLite 更自然。向量库管「找得到」，关系库管「管得好」。

### 2.4 向量化 — `backend/rag/embedding.py`

调硅基流动的 `BAAI/bge-m3`（DeepSeek 没有 Embedding API；硅基流动免费额度足够学习期）：

```python
BATCH_SIZE = 16  # 每次请求最多带 16 条文本（官方上限 32，留余量）

def embed_texts(texts):   # 自动分批 → 按返回的 index 排序 → 拼回原顺序
def embed_query(text):    # 单条查询向量化，检索时用
```

> **本项目踩过的三个真实的坑（面试讲出来极加分）**：
> 1. **入库和查询必须用同一个模型**。不同模型的向量空间完全不同，混用后相似度全错且**不报错**——所以向量化收敛成本文件唯一入口，add 和 query 都从这里拿向量；
> 2. **`load_dotenv()` 时序**：embedding.py 在 import 时就读配置，必须自己先 `load_dotenv()`，否则 main.py 的加载顺序轮不到它，Key 永远是空的；
> 3. **Chroma 1.5 的 collection 名必须 ≥3 字符**，`"kb"` 直接报 `InvalidArgumentError`，改成 `"kb_chunks"` 才过。

### 2.5 向量入库 — `backend/rag/vector_store.py`（Chroma）

```python
_client = chromadb.PersistentClient(path=CHROMA_DIR)   # 落盘，重启不丢
_collection = _client.get_or_create_collection(
    name="kb_chunks",
    metadata={"hnsw:space": "cosine"},   # 余弦相似度，语义检索标准选择
)

def vectorize_document(doc_id):
    chunks = kb_store.get_chunks(doc_id)          # 从 SQLite 取原文分片
    vectors = embed_texts(chunks)                  # 批量向量化
    _collection.add(
        ids=[f"{doc_id}:{i}" for i in range(len(chunks))],   # 如 "3:23" = 文档3的第23片
        embeddings=vectors,
        documents=chunks,                          # 原文一起存，检索时直接返回
        metadatas=[{"doc_id": doc_id, "chunk_index": i} ...],
    )
    kb_store.mark_vectorized(doc_id)               # 打同步标记
```

**关键设计**：传「预计算好的向量」给 Chroma，而不是让它调默认 embedding 函数——保证与查询侧同一模型。id 格式 `doc_id:chunk_index` 让每个向量都能溯源到具体文档的具体分片。

## 三、知识库应用（问答链路）

### 3.1 请求入口 — `ChatRequest` 加了一个字段

```python
class ChatRequest(BaseModel):
    messages: list[ChatMessage]
    knowledge_base_id: int | None = None   # null=普通对话；传 id=RAG 检索问答
```

**同一个接口双模式**：不选库=阶段一的纯流式对话；选了库=先检索再回答。用户在输入框上方的下拉框里切换。

### 3.2 检索 + 拼装 Prompt — `build_rag_context()`

```python
def build_rag_context(question):
    hits = vector_store.search(question, top_n=5)   # ① 语义检索 Top5
    for i, hit in enumerate(hits, start=1):
        blocks.append(f"[{i}] （来源：{hit['filename']}，相关度 {hit['similarity']:.2f}）\n{hit['text']}")
        sources.append({...})                        # ② 记录引用元数据给前端
    return "\n\n".join(blocks), sources
```

`vector_store.search()` 内部：`embed_query(question)` → Chroma `query(n_results=5)` → 相似度 `1 - 余弦距离` 降序返回。

### 3.3 RAG 的灵魂：5 行 System Prompt

```python
RAG_SYSTEM_PROMPT = """你是一个企业知识库问答助手。请严格根据下面的参考资料回答用户问题，
并在答案中用 [1]、[2] 这样的编号标注引用了哪条资料。如果参考资料中没有相关内容，
请直接回答「知识库中没有找到相关资料」，不要编造。

参考资料：
{context}"""
```

拼装方式（`main.py` 的 `chat()`）：

```python
msgs = [{"role": "system", "content": RAG_SYSTEM_PROMPT.format(context=context)}] + msgs
```

> **面试考点**：这个 prompt 做了三件事，缺一不可——
> ①「严格根据资料」**约束幻觉**；②「标注 [1][2]」**产生可溯源引用**；③「没有就说没有」**处理知识库外问题**（拒答能力）。这就是"检索增强"里"增强"的全部含义：不改模型，只改输入。

### 3.4 流式输出增强：先推 sources 事件

```python
def stream_upstream():
    if sources:  # RAG 模式：流的最前面先发一个自定义事件
        yield f"data: {json.dumps({'type': 'sources', 'sources': sources})}\n\n"
    # 之后原样透传 DeepSeek 的 SSE 分片（阶段一的逻辑不变）
```

SSE 是纯文本协议，事件内容本来就是自定义 JSON——复用同一条流，**在正文之前**塞一个 `type: "sources"` 事件，前端解析时按 `type` 分流即可。这是流式协议里「控制消息」的最小实现。

### 3.5 前端三处配合

**① `api/chat.ts` — 解析层加一个分支**：

```ts
if (parsed.type === 'sources' && Array.isArray(parsed.sources)) {
  callbacks.onSources?.(parsed.sources)   // 引用元数据先于正文到达
  continue
}
```

**② `composables/useChat.ts` — 引用挂到消息上**：

```ts
onSources(sources) {
  assistantMsg.sources = sources   // 挂在本次回答的 ChatMessage 上
},
```
`sendMessage(content, knowledgeBaseId)` 把选中的库 id 传进请求体 `knowledge_base_id`。

**③ `App.vue` — 选择器 + 溯源 UI**：
- 输入框上方下拉框选择知识库（未向量化的文档禁用，选中显示「RAG 检索模式」标签）；
- AI 回答气泡底部渲染「引用来源」chips：`[1] knowledge2.pdf`；
- 点击 chip 弹窗展示：文件名、第几分片、相关度百分比、原文片段——**来源溯源闭环完成**。

### 补充：Rerank 与引用角标（同日第二轮）

- **两级漏斗检索**（`rag/rerank.py`）：Chroma 粗排召回 Top20 → 硅基流动 `bge-reranker-v2-m3` 精排取 Top5，失败自动降级为粗排前 5；
- **正文引用角标**（`renderMarkdownWithCitations`）：答案里的 `[1]` 转可点击上标，按 `<code>` 分段替换避免误伤代码；点击经事件委托打开溯源弹窗；
- **检索评估**（`rag/evaluate.py`，运行 `python -m rag.evaluate --sample 20 --seed 42`）：

| 指标 | 纯向量 Top5 | 向量+Rerank Top5 |
|------|------------|------------------|
| 命中率（seed=42，20 样本） | 95.0%（19/20） | **100.0%（20/20）** |
| 命中率（seed=7，20 样本） | 100.0% | 100.0% |
| 平均检索耗时 | ~460ms | +~570ms（重排） |

> 诚实解读（面试就这么说）：评估方法是「截取片段当查询召回原片段」，自检索任务向量检索本就近天花板，小样本下 Rerank 的增益体现在抢救边界 case（+5pp）且**从不劣化**；代价是每次问答多 ~570ms。真实收益要靠人工标注问题集来放大——这正是下一步该做的。

## 六、面试速答卡（30 秒版）

> **Q: 你的 RAG 是怎么实现的？**
> 上传侧：pymupdf 提取 → 500 字滑动窗口+100 重叠分片 → bge-m3 向量化 → Chroma（cosine）落盘，SQLite 管元数据和同步状态。问答侧：问题用同一模型向量化 → Chroma 召回 Top5 → 拼进带编号的 system prompt 约束幻觉 → DeepSeek 流式输出，SSE 流里先推引用元数据事件，前端渲染可点击的来源溯源。踩过的坑：入库和查询 Embedding 模型不一致会导致相似度全错且不报错，所以向量化收敛成唯一入口。
